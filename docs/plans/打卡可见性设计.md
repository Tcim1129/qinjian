# 打卡可见性（visibility）设计

日期：2026-09-21
状态：设计待评审（含 5 个待决策项）
范围：仅设计，不含代码改动

## 1. 背景

移动端契约已定义完整的可见性语义，但后端**完全没有实现**：

| 契约要素 | 后端现状 |
| --- | --- |
| `visibility_scope`: `private` / `shared_summary` / `shared_original`（+ 网页端 `system_only`） | `Checkin` 模型**无** visibility 字段 |
| 创建时 `sharing_confirmed` | 无 |
| 读取 `visibility`：`sharing_active` / `partner_can_use_summary` / `partner_can_read_original` | 无 |
| 乐观并发：`version` / `expected_version` / `known_version` / `not_modified` | 无版本概念 |
| 幂等：`deduplicated` | 无 |
| 撤回失效：`sharing_revoked` / `alignment_results_invalidated` / `derived_insights_invalidated` / `snapshots_invalidated` / `reports_invalidated` | **无任何 invalidate 机制** |
| 安全：`processing_status` / `safety_mode` / `safety_handoff` | 部分（`safety_gate`） |

### 1.1 关键冲突：默认语义两边不一致

- **后端归档现状**（`services/timeline_archive.py:404-422`）：伴侣**始终**能看到一条摘要占位
  （`item_type=partner_record_placeholder`、标题"对方在这天也留下了一条记录"、摘要 + 标签，
  `locked_reason="原文和原媒体默认仅记录者本人可见。"`，`visibility=shared_summary`）。
  即：**今天是"默认共享摘要"**。
- **移动端现状**（`apps/mobile/src/pages/journal/index.vue:216-217`）：硬编码
  `visibility_scope: 'private'`、`sharing_confirmed: false`，界面显示"仅自己可见"。
  即：**移动端认为默认是"仅自己"**。

两者直接冲突。**这是本设计必须最先定的事（见 §9 D1）。**

### 1.2 现有可复用的资产

- `Checkin.raw_retention_until` / `raw_deleted_at`：原文与原媒体的生命周期字段**已存在**，
  可见性设计应复用它，而不是另造一套。
- 归档序列化已实现"摘要对伴侣可见、原文/原媒体仅本人"的完整逻辑
  （`serialize_archive_checkin_item`），`shared_summary` 可直接对齐它。
- 派生结果存储位置已明确：
  - 对齐结果 → `RelationshipEvent(event_type="alignment.generated")`，键为
    `alignment:{pair_id}:{checkin_a_id}:{checkin_b_id}`（`insights_routes/alignment.py:81-86`）
  - 快照 → `relationship_profile_snapshots`（**已有 `version` 列**）
  - 报告 → `reports`
  - 派生洞察 → `relationship_memories` + `relationship_events`
- 语音线（独立分支）已有成熟的授权共享模型
  （`emotimirror_consent_receipts` + `emotimirror_authorized_shared_contents`：哈希校验、版本、
  `sealed→submitted→purged` 生命周期、`revoked_at`、`purge_reason`）。长期应向它收敛。

## 2. 术语映射

契约与归档用了两套词，必须建立唯一映射，避免第四套命名。

| 契约 `visibility_scope` | 归档 `visibility` | 伴侣可读 | 伴侣可读原文/原媒体 | 系统可分析 |
| --- | --- | --- | --- | --- |
| `private` | `owner_only` | 否（完全看不到） | 否 | 是 |
| `shared_summary` | `shared_summary` | 仅摘要/标题/标签 | 否 | 是 |
| `shared_original` | `shared_original`（新增） | 摘要 + 原文 | 是（需显式授权） | 是 |
| `system_only` | `system_only`（新增） | 否 | 否 | 是（**仅系统内部使用**） |

说明：

- `private` 与 `owner_only` 是同一语义，建议**对外统一用契约词**，归档序列化输出做映射。
- `system_only` 仅出现在网页端 `CheckinVisibilityUpdateRequest`，移动端契约没有。语义建议：
  **任何人（含记录者本人）不可读原文，仅参与系统分析与派生**。用于自动化/系统生成内容。
- `shared_report`（归档里报告项的现有值）不在契约 scope 内，属于**报告项**而非打卡项，保持不变。

## 3. 数据模型

### 3.1 `checkins` 增列

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `visibility_scope` | `String(20)`，非空，默认见 §9 D1 | `private` / `shared_summary` / `shared_original` / `system_only` |
| `visibility_version` | `Integer`，非空，默认 `1` | 乐观并发版本；每次变更 +1 |
| `sharing_confirmed_at` | `DateTime`，可空 | 记录者确认共享的时刻；`private` 时为 NULL |
| `visibility_updated_at` | `DateTime`，可空 | 最近一次可见性变更时刻 |

约束：`visibility_scope IN (...)` CHECK；`shared_summary`/`shared_original` 必须
`sharing_confirmed_at IS NOT NULL`（共享必须有确认记录）。

### 3.2 新增追加式审计表 `checkin_visibility_events`

沿用本项目"追加式证据"风格（参考语音线 advanced evidence 的做法），**只增不改**：

| 列 | 说明 |
| --- | --- |
| `id` | PK |
| `checkin_id` | FK → checkins，级联 |
| `actor_user_id` | 操作者 |
| `from_scope` / `to_scope` | 变更前后 |
| `from_version` / `to_version` | 版本递增 |
| `sharing_confirmed` | 本次是否携带确认 |
| `client_request_id` | 幂等键 |
| `invalidated` | JSON：本次失效的派生结果计数（见 §6） |
| `created_at` | |

数据库触发器禁止 UPDATE/DELETE（仅允许隐私删除）。

### 3.3 复用现有字段

原文/原媒体生命周期继续用 `raw_retention_until` / `raw_deleted_at`，
**不因可见性变更而删除**；可见性只控制"谁可读"，保留策略独立。

## 4. 权限矩阵

| 读取者 | `private` | `shared_summary` | `shared_original` | `system_only` |
| --- | --- | --- | --- | --- |
| 记录者本人 | 全文 + 媒体 | 全文 + 媒体 | 全文 + 媒体 | **不可读原文**（见 §9 D3） |
| 伴侣 | 不可见（列表无此项） | 仅摘要/标签，`locked_reason` 提示 | 摘要 + 原文 + 媒体 | 不可见 |
| 系统/分析 | 可分析 | 可分析 | 可分析 | 可分析 |

派生字段（供接口返回）：

- `sharing_active`：`scope != private`（对伴侣而言是否存在共享关系）
- `partner_can_use_summary`：`scope in (shared_summary, shared_original)`
- `partner_can_read_original`：`scope == shared_original`

**默认拒绝**：任何未显式匹配的组合一律按最严格处理。

### 4.1 伴侣投影（partner projection）—— 摘要不是原文，但仍需去敏

`shared_summary` 下伴侣看到的是 `archive_summary` / `archive_title` / `archive_tags`，
它们由 `build_checkin_archive_insight`（`services/timeline_archive.py:163`）生成，
来源是**关键词词典规则**（`summarize_text_emotion`，`services/behavior_judgement.py:353`），
**不含原文**。但现状有泄露点，必须做一层伴侣投影：

| 泄露点 | 现状 | 伴侣投影要求 |
| --- | --- | --- |
| 风险标记 | 摘要含「系统把它标记为值得留意」 | **剥离**，伴侣不可见 |
| 危机/冲突意图 | 摘要含「更像需要保护」「更像冲突处理中」 | **剥离**或降级为中性表述 |
| 情绪标签 | 由原文关键词匹配得出，可被反推 | 保留，但限制到**低敏感词表**；高敏感标签不出现在伴侣侧 |
| 图片场景摘要 | AI 对画面的描述，较具体 | 默认**不向伴侣展示**，仅提示"附带了一张图片" |
| 语音 | 时长可展示 | 时长可展示，内容与分析不可 |

原则：**伴侣侧只回答"对方今天有记录、大致情绪如何"，不回答"对方说了什么、发生了什么"。**
必须加一条测试：伴侣可见的摘要文本不得包含原文子串，也不得包含风险/危机标签。

`private` 下伴侣连摘要占位都没有（列表不出现该项）。

## 5. 接口（阶段 1 需要）

### 5.1 创建

`POST /mobile/checkins`

```
{ scope, relationship_space_id?, client_request_id, content, mood_score?, mood_tags?,
  image_url?, voice_url?,
  visibility_scope?: "private"|"shared_summary"|"shared_original",
  sharing_confirmed?: boolean,
  client_context? }
→ { record_id, scope, relationship_space_id?, checkin_date, deduplicated,
    visibility_scope, processing_status: "queued"|"safety_handoff",
    safety_mode?, safety_handoff?, data_minimized? }
```

校验：

- `visibility_scope` 缺省 → 取默认（§9 D1）
- `visibility_scope != private` 且 `sharing_confirmed != true` → **422 拒绝**（不允许静默共享）
- `scope == solo` 且 `visibility_scope != private` → 422（单人空间无可共享对象）
- `client_request_id` 重复 → 返回原记录，`deduplicated=true`
- 命中安全拦截 → `processing_status="safety_handoff"`，`safety_mode=true`，附 `safety_handoff` 文案

### 5.2 读取可见性

`POST /mobile/checkins/visibility`

```
{ record_id, known_version? }
→ { record_id, relationship_space_id?, visibility_scope,
    sharing_active, partner_can_use_summary, partner_can_read_original,
    version, not_modified, deduplicated, data_minimized? }
```

- `known_version` 与当前一致 → `not_modified=true`（其余字段仍返回，供前端缓存）
- 非本人且非伴侣 → 404（不泄露存在性）

### 5.3 变更可见性

`POST /mobile/checkins/visibility/change`

```
{ record_id, expected_version, visibility_scope, sharing_confirmed? }
→ { record_id, visibility_scope, version, sharing_revoked,
    alignment_results_invalidated, derived_insights_invalidated,
    snapshots_invalidated, reports_invalidated, deduplicated, data_minimized? }
```

- `expected_version != 当前版本` → **409**（乐观并发冲突），返回当前 `version` 供前端重取
- 从共享态 → `private`/`system_only`：`sharing_revoked=true`，触发 §6 失效
- 进入共享态必须 `sharing_confirmed=true`
- 仅记录者本人可变更（伴侣/他人 403）

### 5.4 详情

`POST /mobile/checkins/detail` 返回内容按 §4 矩阵裁剪；非授权读取不返回原文。

## 6. 撤回与派生结果失效

撤回（从共享态变为 `private`/`system_only`）必须让**基于该记录的派生结果失效**，否则伴侣仍能从报告/对齐/快照间接读到内容——这是隐私漏洞，不是可选项。

| 派生结果 | 存储 | 失效方式 |
| --- | --- | --- |
| 对齐结果 | `RelationshipEvent(event_type="alignment.generated")`，键含 `checkin_a_id`/`checkin_b_id` | 按记录 ID 定位含该记录的缓存事件，标记失效 |
| 快照 | `relationship_profile_snapshots` | 追加失效标记并**提升版本**（已有 `version` 列） |
| 报告 | `reports` | 将涉及该记录的日报/周报标记为需重算 |
| 派生洞察 | `relationship_memories` / `relationship_events` | 标记失效，不再参与对外展示 |

设计原则：

1. **标记失效 + 版本失效，不物理删除**（保留可审计性）；物理清除仍由隐私删除流程负责。
2. 失效操作**幂等**：重复撤回不重复计数。
3. 返回计数与契约字段一一对应（`*_invalidated`）。
4. 失效在**同一事务**内完成，避免"已撤回但报告仍可读"的中间态。
5. 失效后重新生成派生结果时，必须**排除**已撤回记录。

## 7. 版本与幂等

- **版本**：`visibility_version` 单调递增；所有变更接口用 `expected_version` 做 CAS，
  冲突返回 409 + 当前版本。读取接口用 `known_version` 做 `not_modified` 短路。
- **幂等**：写接口用 `client_request_id`（移动端已生成）去重；重复请求返回首次结果并置
  `deduplicated=true`。去重表建议复用现有 request-cooldown/幂等存储，不新造。

## 8. 安全边界

- 共享必须**显式确认**（`sharing_confirmed`），任何默认共享都视为缺陷。
- 伴侣侧永不返回原文/原媒体，除非 `shared_original`。
- 不泄露存在性：无权限访问一律 404，而非 403 区分。
- 撤回必须级联失效派生结果（§6），并记录审计事件。
- 安全拦截（危机信号）优先于可见性：命中时走 `safety_handoff`，不进入普通共享。
- 本文的可见性**不等于**语音线的 consent receipt；后者带哈希校验与到期。
  长期应把打卡共享纳入同一授权模型（见 §9 D5）。

## 9. 待决策项

| 编号 | 决策 | 建议 |
| --- | --- | --- |
| **D1** | **默认 `visibility_scope`** | **建议 `shared_summary`**（已按产品判断定案）：伴侣看到**去敏后的摘要**，永远看不到原文；`private` 保留为**逐条显式选择**（连摘要都不给看）。理由：关系产品的核心是"互相看见"，完全不可见会让共享空间变空、共同仪式断裂导致流失；而摘要（情绪/意图层面的派生标签，非原文）足以制造在场感与话题，同时保护最敏感的原文。附加好处：不改变现有默认行为，迁移风险最低。**前提是必须先实现 §4.1 伴侣投影**，否则风险/危机信息会漏给伴侣。 |
| D2 | 是否开放 `shared_original`（伴侣可读原文） | 建议阶段 1 **先不开放**（仅 `private` / `shared_summary`），原文共享涉及冒用与安全风险，单独评审。 |
| D3 | `system_only` 是否对本人也不可读 | 建议：是（否则等同 `private`）。仅用于系统生成内容。 |
| D4 | 撤回时标记失效 vs 物理删除 | 建议标记失效 + 版本失效（可审计），物理清除交给隐私删除流程。 |
| D5 | 何时与语音线 consent receipt 统一 | 建议阶段 1 先落地自有实现，接口形状与 consent 语义对齐，待语音线集成时收敛。 |

## 10. 迁移与兼容

- 新增列对既有 `checkins` 行回填：按 D1 决策统一回填，**不要**用 `NULL` 表示未知。
- 回填 `visibility_version=1`、`sharing_confirmed_at` 按回填后的 scope 决定。
- 归档序列化（`serialize_archive_checkin_item`）需按新 scope 调整：
  当前"伴侣总能看到摘要"的行为要改为按 `visibility_scope` 判定。
- 迁移编号接在网页线当前 head `7c5e9210abcd` 之后。

## 11. 验收

- 权限矩阵：4 个 scope × {本人, 伴侣, 他人} 全部用例。
- **伴侣投影**：伴侣可见摘要不含原文子串、不含风险/危机标签、不含图片场景描述（§4.1）。
- 共享未确认 → 拒绝；默认不共享。
- 乐观并发：错误 `expected_version` → 409。
- 幂等：重复 `client_request_id` → `deduplicated=true` 且不重复写入。
- **撤回后伴侣无法从记录、归档、报告、对齐、快照任一路径读到内容**（核心安全验收）。
- 单人空间不允许非 `private`。
- 安全拦截优先于可见性。
